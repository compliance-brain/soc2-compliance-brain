# Agent instructions

This repository is a compliance program for one company, plus the library and guardrails an AI agent needs to build and run it. If you are an AI agent, this file is your brief. Read it before doing anything else, whatever tool you are running in.

## Start of every session

1. Read this file, then [brain/guidance/ai-guidance.md](brain/guidance/ai-guidance.md). The guidance holds your standing guardrails, and its section numbers (for example 0.7 or 9.4) are cited throughout the repo.
2. Read [program/context/profile.yaml](program/context/profile.yaml) and [program/context/README.md](program/context/README.md). The profile holds the facts about the company; treat its answers as facts from the client.
3. Run `python3 tools/scope.py` and `python3 tools/check.py` to see what's in scope and what's still open.
4. Read the last 10 rows of [program/records/audit-trail.csv](program/records/audit-trail.csv) to see what happened last time.

## What to do

1. **Check Program home first.** If it's TBC, ask where the program should live. Options, in order: this repository; knowledge and work tools (Notion, monday.com); workspace suites (Google Workspace, Microsoft 365); then compliance platforms (Vanta, Drata, Secureframe, Delve, Sprinto). Favour what the team already uses. If the program lives somewhere else, keep the profile, library and audit trail here, build the records there, and note what lives where in the profile.
2. **Set up the context.** Ask for the high-impact sources the company already has, such as completed security questionnaires, terms of service, privacy policy, trust page and operating manuals. Log them in [context-sources.csv](program/context/context-sources.csv), draft profile answers from them and cite the source. Fill high-impact (H) fields first; TBC is fine.
3. **Generate the control framework early.** Once the H fields are answered, run `tools/scope.py`, then build [control-list.csv](program/controls/control-list.csv) from [scope.md](program/controls/scope.md). This list is what the company will be audited on and collect evidence for, and it will change over time.
4. **Keep it simple.** Build a lean first cut sized to the company's stage (AI Guidance 10), mark decisions still to be made as Confirm items, and say plainly where the setup is complex (9.6).
5. **Never make anything up.** Record only what the client told you, what you saw in their systems, or a public source you checked. Check assumptions before you record or rely on them.
6. **Ask when it matters.** If a missing detail is critical to the work, stop and ask. If it's minor, add a Confirm item and carry on (9.2 to 9.5).
7. **Ask before acting on anything that matters.** Ask before anything irreversible, anything that changes systems, access or policies, or anything that leaves the company. People change security settings themselves: prepare the change, guide them and capture the evidence (0.3).
8. **Log each block of work.** Add one row to [audit-trail.csv](program/records/audit-trail.csv) and make one commit per block of work (see below).

## Working rules for this repository

- **Edit `program/`, not `brain/`.** `brain/` is the shared library. If something in it is wrong or missing, tell the user and suggest raising it upstream.
- **Keep the structure.** Don't rename CSV columns or files. Use option values exactly as listed in [field-options.csv](brain/library/field-options.csv). Separate several answers with commas.
- **Use the markers.** `{{like this}}` is something to replace. In Markdown, `> [!NOTE]` 🧭 Guide boxes explain, `> [!IMPORTANT]` ✏️ Adapt boxes say what to customise, and `> [!WARNING]` ✅ Confirm boxes hold decisions for the owner. Rows starting "Example:" show the format; replace or delete them. Delete Guide and Adapt boxes once a document is adapted. Keep Confirm items until they are resolved or accepted at sign-off.
- **Records are append-only.** Add new rows at the bottom of `audit-trail.csv` and `sign-off-log.csv`. If a row is wrong, add a correcting row that refers to the original.
- **People approve; you draft.** A policy is approved when the approver merges the pull request (or confirms in writing), a row is added to `sign-off-log.csv`, and the policy header is updated. Never mark something approved yourself.
- **Commits.** One commit per block of work, with a message that matches the audit trail entry, for example `Draft Access Control Policy (AUDT-7)`. If you can, work on a branch and open a pull request so a person reviews the change.
- **No secrets.** Never commit passwords, keys, tokens, customer content or unnecessary personal data. Link to evidence rather than copying sensitive content. Keep this repository private.
- **Run the tools.** Run `tools/scope.py` after any profile change, and `tools/check.py` before you report progress.
- **If you can't write here,** give the user the exact changes to apply.

## Before anything goes to an auditor

Run `python3 tools/check.py --strict`. Nothing generic should be left, every Confirm item should be resolved or recorded as accepted in the sign-off log, and every AI change in the audit trail should have a reviewer. The Compliance Owner reviews anything likely to raise an exception before it reaches the auditor (0.7). Never alter, back-date or manufacture evidence.
